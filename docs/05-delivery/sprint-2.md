### Assumptions (for review by software-architect and security-reviewer)
1. **`access` reads the `students` and `platform_profiles` tables directly and read-only** (like the `today` and `health` read models). Reason: `students → identity → access`, and going through `students.service` would create an import cycle. That is why `students/activity.ts`, `students/erasure.ts` and `path/transitions.ts` are separate files that import only from schema.
2. **The students module repo has read-only JOINs with `users`, `stages`, `tracks` and `platforms` for display** (name, phone number, account status). Writes always happen in the module that owns the table.
3. **An admin without `mentorId` creates a student with no mentor** (data-model: "empty = unassigned"). The UI can default to the admin themselves. `PUT /students/:id/mentor` also accepts `mentorId: null`.
4. **The direction of a stage transition matches its kind:** `regress` only backwards; `advance`, `skip_by_assessment` and `advance_with_exception` only forwards (skipping is allowed). Same stage or wrong direction → `409 INVALID_TRANSITION`. The target stage must be active (`422`).
5. **`daysInStage` = full days since `stage_entered_at`** (24-hour days, not Tehran day boundaries). `overExpected`: more than `expectedDays` → `warn`, more than 2× → `over`; an open-ended or durationless stage → `none`.
6. **The kanban** shows `active` and `paused` students (with `lifecycleStatus` on the card); within a column, most days first.
7. **"My path":** stages before the current one are `passed`, those after it `locked` (finer detail, such as `passed_by_assessment`, is only visible to staff in the history). An inactive stage is shown only if it is the student's current stage.
8. **`SelfStudentDTO`** lacks, in addition to health, flag, tag and cohort, also `level`, `statusReason`, `lifecycleStatus`, `lastActivityAt` and the mentor's ID (only the mentor's name). It sees `niche_statement` but cannot edit it (data-model allowlist).
9. **Pagination of `GET /students`** uses an opaque cursor (encoded offset); enough for at most 500 students (overview 6). A forged cursor → `422`.
10. **Health filtering and sorting** (`health=`, `sort=health`) are not accepted until the health module exists (`422`, unknown key). The `health`, `nextTask`, `openTaskCount`, `overdueTaskCount` fields are currently `null`/`0`.
11. **`initialNote` in `POST /students`** is not in the schema until the `notes` table is built (sprint 3) (sending it → `422`).
12. **Profile rate currency:** if an amount is given and no currency, it becomes `USD`. The amount is returned as a decimal string (`"25.00"`).
13. **A deleted profile is non-existent for everyone** (`404`), including approval and snapshots. Editing an approved profile does not remove the approval.
14. **`PATCH /stages/:id` does not deactivate** (`isActive: false` → `422`); only `POST /stages/:id/deactivate`, which checks for active students. `paused`/`graduated`/`dropped` students do not block deactivation.
15. **`PUT /stages/order`** requires all stages (active and inactive) and rewrites `sortOrder` as 10, 20, ….
16. **`pausedUntil`** must be after today in Tehran; it must not be sent for other statuses.
17. **The seed runs in `db:migrate`** (not inside `runMigrations` itself), so the Docker migrator (`db:migrate`) also seeds, and the CLI test that needs an empty database is not affected.
18. **`profile_snapshots.source_submission_id`** has no FK for now; it is added together with the `submissions` table in sprint 3.

## Frontend guide (for frontend-engineer)

### General rules
- RSC pages call service functions **directly**; the first parameter is `actor`:
  ```ts
  const user = await requireUser(['admin', 'mentor']);
  const list = await listStudents(toActor(user), { q, stageId, sort: 'name' });
  ```
  `requireUser` and `toActor` come from `@/server/auth/current-user`.
- Errors are `ApiError` (`@/server/http/errors`) with `code`, `status`, a Persian `message` and `fields`. On a single-item page: `NOT_FOUND` → `notFound()`; `FORBIDDEN` should not occur if the layout restricts the role correctly.
- **Writes only through the API** (Server Actions are forbidden, SEC-A10). Client forms use `fetch` with `Content-Type: application/json` (the browser sends `Origin` itself).
- DTOs are types only, and importing them in client components is allowed: `import type { … } from '@/modules/students/contracts'`. **The zod schemas in these same files** can also be used for client-side validation (react-hook-form); but never import the service file on the client.
- All dates are ISO with `Z`; `pausedUntil` is a Tehran day `YYYY-MM-DD`. Jalali display is done by the UI.
- `422` response: `error.fields.<field name>` is a Persian message ready to show next to the field; an invalid reference ID always gives "Invalid value".
- The `health` and `nextTask` fields are currently `null` and task counts are `0`; the UI should show a "No data yet" state.

### Frontend gaps (for backend-engineer; worked around with existing functions for now)
1. **`StudentListDTO` has no total count.** The status chip counters and the tag list are built by paging through `listStudents(lifecycle=all, limit=100)` (max 10 pages; `app/(staff)/_data.ts`). Proposal: a `counts: { byLifecycle, total }` field and a `GET /students/tags` endpoint.
2. **`StudentListItemDTO` has no `overExpected` field** (the record and kanban DTOs do). The page computes it with `overExpected` from `students/policy` and `listStages`. Proposal: add it to the list DTO.
3. **`BoardStudentDTO` has no `accountStatus` field** (needed for "Not signed in yet" on the card).
4. **`StageRef` does not include the stage's position.** The path bar index is taken from `listStages`. If the student's current stage is inactive, a mentor (who has no `includeInactive`) sees position 0, and the transition direction in the dialog may be guessed as `advance`.
5. **A mentor cannot tell whether `mentorsCanInviteStudents` is on** (until `GET /settings` is built). The button is always shown and a 403 is answered with a clear message.
6. **The `409 PHONE_TAKEN` response offers no way to "Go to the existing record"** (user-flows §1). If needed, for admins only and only within their scope.
