# ADR-0007 — کارهای پس‌زمینه و زمان‌بندی: pg-boss روی همان Postgres

- **وضعیت:** پیشنهادشده
- **تاریخ:** ۲۷ مهر ۱۴۰۵ (2026-10-19)
- **نویسنده:** software-architect

## زمینه
- 0.1 چند کار زمان‌بندی‌شده دارد: `health.sweep` (ساعتی)، پاک‌سازی نشست‌ها و توکن‌های منقضی، پاک‌سازی پیوست‌های وصل‌نشده.
- 1.0 صف واقعی لازم دارد: فراخوانی LLM با تلاش مجدد و timeout، و ارسال اعلان پیامکی/تلگرامی.
- نمی‌خواهیم سرویس دیگری (Redis) نگه داریم یا به زمان‌بند میزبان (Vercel Cron، Azure Functions) قفل شویم (ADR-0002).

## گزینه‌ها
| گزینه | ارزیابی |
|---|---|
| **pg-boss** | صف و cron روی Postgres؛ زمان‌بندی با منطقه‌ی زمانی؛ cron در چند نمونه‌ی برنامه فقط یک بار اجرا می‌شود؛ تلاش مجدد، singleton و انقضا دارد؛ با `pg_dump` جابه‌جا می‌شود |
| graphile-worker | خوب و سریع؛ ولی cron آن پیکربندی جدا می‌خواهد. هم‌ارز است؛ pg-boss به‌خاطر API ساده‌تر انتخاب شد |
| BullMQ + Redis | سرویس دوم؛ رد |
| node-cron داخل پردازه | با دو نمونه‌ی برنامه دو بار اجرا می‌شود؛ صف ندارد؛ رد |
| زمان‌بند میزبان | قفل‌شدگی؛ رد (فقط به‌عنوان «محرک»، پایین) |

## تصمیم
- **pg-boss** در schema جدای `pgboss` همان دیتابیس.
- سه حالت با `JOBS_MODE`:
  - `in-process` (پیش‌فرض Azure و میزبان ایرانی): هنگام بالا آمدن سرور Next.js (`instrumentation.ts`، فقط در runtime Node) pg-boss شروع می‌شود، scheduleها ثبت و workerها فعال می‌شوند. **App Service باید «Always On» باشد.**
  - `http-trigger` (اگر روزی روی سرورلس رفتیم): workerها اجرا نمی‌شوند. زمان‌بند بیرونی `POST /api/internal/jobs/:name` را با سرآیند `X-Job-Secret` صدا می‌زند و همان handler یک بار اجرا می‌شود.
  - `off`: برای تست.
- هر job **idempotent** است و handler آن یک تابع service معمولی است (`health.service.sweepAll()`)، پس از هر سه حالت و از تست قابل‌فراخوانی است.

### jobهای 0.1
| نام | زمان‌بندی (Asia/Tehran) | کار |
|---|---|---|
| `health.sweep` | `5 * * * *` | ADR-0005 |
| `health.sweep` (فوری) | با تغییر `health.rules` | — |
| `auth.cleanup` | `30 3 * * *` | حذف نشست‌ها و توکن‌های منقضی بیش از ۷ روز؛ پاک کردن `auth_throttle` کهنه. (امنیت C5، ADR-0010) نگه‌داری `audit_log`: `ip ← null` برای ردیف‌های بیش از ۹۰ روز؛ حذف ردیف‌های بیش از ۲۴ ماه **جز** `user.erased`. (job تازه‌ای ساخته نمی‌شود تا فهرست سفید endpoint داخلی، SEC-J3، همان سه نام بماند) |
| `files.cleanup` | `45 3 * * *` | حذف پیوست‌های `pending` بیش از ۲۴ ساعت (رکورد و فایل) |

پشتیبان‌گیری job برنامه **نیست** و مسئولیت زیرساخت است (devops-engineer؛ ADR-0002 بخش ۶)، تا خرابی برنامه پشتیبان را متوقف نکند.

### jobهای 1.0 (فقط برای نشان دادن جا)
`ai.run` (تلاش مجدد ۲ بار، timeout ۶۰ ثانیه، هم‌زمانی محدود)، `notify.send`، `digest.daily`.

### تطبیق با پیاده‌سازی (هماهنگ با کد، اسپرینت ۱ تا ۴؛ ۳۰ مهر ۱۴۰۵)
| موضوع | آنچه ساخته شد | حکم |
|---|---|---|
| ثبت jobها | `src/server/jobs/index.ts`: سه job جدول بالا با `boss.schedule(name, cron, null, { tz: 'Asia/Tehran' })`؛ `instrumentation.ts` پیش از آن `getEnv()` را صدا می‌زند (env نامعتبر ← سرور بالا نمی‌آید). شکست شروع pg-boss سرور وب را پایین نمی‌آورد و فقط لاگ می‌شود (اسپرینت ۱ و ۴) | پذیرفته؛ کهنگی sweep را `/healthz` نشان می‌دهد |
| `health.sweep` (فوری) | **صف نمی‌شود**: تغییر `health.rules`، `checkin` یا `expectedDays`/`isOpenEnded` مرحله `sweepAllHealth()` را داخل همان درخواست پس از commit (best-effort) صدا می‌زند (اسپرینت ۴) | پذیرفته برای حجم 0.1 (ADR-0005). ردیف «فوری» جدول بالا یعنی همین فراخوانی، نه job |
| `health.sweep` | پیش از محاسبه، بازگشت خودکار توقف‌های تمام‌شده (`students/lifecycle-auto.ts`) | هم‌خوان با ADR-0005 |
| `auth.cleanup` | (اسپرینت ۱) نشست‌ها و توکن‌های منقضی/مصرف‌شده‌ی بیش از ۷ روز، `auth_throttle` کهنه، و نگه‌داری `audit_log` (IP پس از ۹۰ روز، ردیف پس از ۲۴ ماه جز `user.erased`). مدت نگه‌داری توکن **عوض نمی‌شود**؛ نمایش «دعوت پذیرفته شد» از ستون‌های `users` می‌آید (ADR-0003 بند 9-9) | پذیرفته |
| `files.cleanup` | (اسپرینت ۳) پیوست `pending` بیش از ۲۴ ساعت، و ردیف‌هایی که حذف فایلشان در حذف حساب شکست خورده | پذیرفته |
| `POST /api/internal/jobs/:name` | (اسپرینت ۴) جز `JOBS_MODE=http-trigger` همیشه `404`؛ `X-Job-Secret` با مقایسه‌ی ثابت‌زمان روی SHA-256، غلط ← `404` + لاگ هشدار؛ فقط سه نام بالا؛ بدنه نادیده؛ ۶۰ بار در ساعت؛ secret کوتاه‌تر از ۳۲ بایت ← برنامه بالا نمی‌آید (SEC-J1..J3) | هم‌خوان |
| `/healthz` | (اسپرینت ۴) `getLastHealthSweepAt()` وصل است: `{ status: 'ok', db: 'ok', lastHealthSweepAt }`؛ خطای دیتابیس ← `503 { status: 'error', db: 'unreachable' }` | **سؤال باز اسپرینت ۴ بسته شد.** باقی‌مانده: هم‌سان‌سازی با SEC-J4 (`ok`، `db: 'fail'`، `version`) و پرچم `sweepStale` (آخرین sweep قدیمی‌تر از ۳ ساعت) برای هشدار devops-engineer (F-08) |

## پیامدها
- **مثبت:** بدون سرویس اضافه؛ قابل‌انتقال؛ همان زیرساخت در 1.0 صف AI است.
- **منفی:** بار صف روی دیتابیس اصلی است؛ برای حجم ما ناچیز است. اگر در 1.0 بار AI زیاد شد، worker با همان image و `JOBS_MODE=worker-only` جدا اجرا می‌شود.
- مانیتورینگ: `/healthz` زمان آخرین اجرای موفق `health.sweep` را برمی‌گرداند. devops-engineer روی آن هشدار می‌گذارد.
