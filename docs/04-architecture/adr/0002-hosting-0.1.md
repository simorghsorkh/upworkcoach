# ADR-0002 — میزبانی نسخه‌ی 0.1: Azure یا Vercel

- **وضعیت:** پیشنهادشده (منتظر گیت بنیان‌گذار)
- **تاریخ:** ۲۷ مهر ۱۴۰۵ (2026-10-19)
- **نویسنده:** software-architect
- **ورودی:** تصمیم بنیان‌گذار (۲۷ مهر ۱۴۰۵، از طریق مدیر پروژه): «فعلاً سرور را روی Vercel یا Azure بالا می‌آورم.»
- **مرتبط:** ADR-0001 (استک)، ADR-0006 (لایه‌ی AI)، ADR-0007 (کارهای پس‌زمینه)

---

## ۱. زمینه

- بنیان‌گذار تصمیم گرفته 0.1 روی **Vercel یا Azure** میزبانی شود. این ADR بین این دو انتخاب می‌کند و ریسک‌ها را صریح می‌گوید.
- 0.1 برای ۳۰ تا ۸۰ هنرجو، ۱ مدیر و ۲ تا ۴ مشاور است (فرض A1). بار بسیار کم است.
- 0.1 به کارهای زمان‌بندی‌شده نیاز دارد: بازمحاسبه‌ی ساعتی وضعیت سلامت (ADR-0005) و پاک‌سازی نشست‌ها و توکن‌ها. یادآورها در 0.1 فقط درون‌برنامه‌اند و job لازم ندارند (ADR-0005، بخش ۶).
- پیوست تصویر تا ۵ مگابایت در 0.1 «Should» است (PRD، F4).
- توسعه‌دهنده یک نفر است و نگهداری ساده مهم است.

### تناقض با PRD (حل‌شده در این ADR)
PRD (بخش ۸ و فرض A4) و `mvp-scope.md` می‌گویند: «0.1 بدون وابستگی به سرویس خارجی و **قابل‌میزبانی در ایران**». با تصمیم بنیان‌گذار این الزام **دیگر برقرار نیست**. از این ADR به بعد الزام معماری این است:

> **0.1 قابل‌انتقال به میزبان ایرانی است**: هر زمان لازم شد، همان image داکر، همان Postgres استاندارد و همان کد، بدون بازنویسی، روی یک سرور ایرانی بالا می‌آید (بخش ۶).

خود PRD ویرایش نشد. مدیر پروژه باید این تغییر را در `STATUS.md` ثبت کند. الزام «بدون CDN و فونت از سرویس‌های خارجی» همچنان برقرار است، چون مرورگر کاربر نباید به دامنه‌ی خارجی دیگری وابسته باشد (هر دامنه‌ی اضافه یک نقطه‌ی فیلتر است).

## ۲. گزینه‌ها

### گزینه‌ی A — Azure: App Service (کانتینر لینوکس) + Azure Database for PostgreSQL Flexible Server + Azure Blob Storage
- برنامه یک **image داکر** است (Next.js با خروجی `standalone`) که روی App Service Linux پلن B1 با «Always On» اجرا می‌شود.
- پردازه دائمی است، پس صف و زمان‌بند **pg-boss** داخل همان پردازه اجرا می‌شود (ADR-0007). سرویس زمان‌بندی اختصاصی Azure لازم نیست.
- دیتابیس: Flexible Server، سطح Burstable، اندازه‌ی **B1ms** (۱ vCore، ۲ گیگ RAM)، ۳۲ گیگ دیسک، پشتیبان خودکار ۷ روزه.
- فایل‌ها: Blob Storage، پشت یک آداپتور (بخش ۶).

### گزینه‌ی B — Vercel Pro + Neon Postgres (از Vercel Marketplace) + Vercel Blob
- Next.js به‌شکل توابع سرورلس (Fluid compute) اجرا می‌شود.
- زمان‌بندی با **Vercel Cron** که یک endpoint را صدا می‌زند. صف دائمی (pg-boss worker) ممکن نیست، چون پردازه‌ی همیشه‌روشن نداریم.
- دیتابیس: Neon (سرورلس، scale-to-zero)، با pooler برای اتصال‌های سرورلس.

## ۳. مقایسه

| معیار | A — Azure | B — Vercel + Neon |
|---|---|---|
| **Postgres مدیریت‌شده** | Flexible Server B1ms؛ Postgres استاندارد؛ پشتیبان خودکار؛ افزونه‌ها (`pg_trgm`، `unaccent`) با پارامتر `azure.extensions` فعال می‌شوند | Neon؛ Postgres استاندارد؛ پلن Launch با بازیابی تا ۷ روز؛ پلن رایگان فقط ۶ ساعت بازیابی دارد، که برای داده‌ی واقعی کم است |
| **کارهای زمان‌بندی‌شده** | داخل پردازه با pg-boss (cron با منطقه‌ی زمانی `Asia/Tehran`)؛ بدون سرویس اضافه | Vercel Cron: روی Hobby فقط **روزی یک بار** و با دقت ±۵۹ دقیقه؛ روی Pro هر دقیقه ([مستندات Vercel](https://vercel.com/docs/cron-jobs/usage-and-pricing)، به‌روزشده 2026-07-15). بازمحاسبه‌ی ساعتی سلامت به **Pro** نیاز دارد |
| **صف برای 1.0 (فراخوانی LLM)** | همان pg-boss؛ worker دائمی | worker دائمی نداریم؛ باید Vercel Workflows یا Queues (سرویس اختصاصی) یا cron هر دقیقه استفاده شود. **قفل‌شدگی** |
| **ذخیره‌ی فایل** | Blob Storage. API آن S3-compatible نیست، پس آداپتور لازم است. آپلود از سرور می‌گذرد و محدودیت حجم نداریم | Vercel Blob (API اختصاصی). بدنه‌ی درخواست به تابع حداکثر **۴٫۵ مگابایت** است ([مستندات Vercel](https://vercel.com/docs/functions/limitations)، به‌روزشده 2026-08-24). پیوست ۵ مگابایتی باید مستقیم از مرورگر به Blob برود، یعنی مسیر دوم آپلود و کد اختصاصی |
| **قابلیت انتقال** | **زیاد**: همان image داکر روی هر VPS ایرانی با Docker Compose اجرا می‌شود | متوسط: کد Next.js قابل‌انتقال است، ولی Cron و Blob و تنظیمات سرورلس باید جایگزین شوند |
| **راه‌اندازی و نگهداری** | متوسط: یک‌بار تنظیم App Service، رجیستری image و دیتابیس. بعد از آن استقرار با push به CI | **خیلی ساده**: push به گیت = استقرار؛ preview برای هر شاخه |
| **تعداد حساب خارجی** | ۱ (Microsoft) | ۲ (Vercel و Neon)، هر کدام با شرایط تحریم خودش |
| **استفاده‌ی تجاری** | مجاز | Hobby فقط «personal or non-commercial» است ([Vercel Terms](https://vercel.com/legal/terms)، بند ۴، به‌روزشده 2026-06-01). پس **Pro لازم است** |
| **نزدیکی منطقه به ایران** | منطقه‌ی UAE North (دبی) وجود دارد و B1ms آنجا موجود است ([Bytebase](https://www.bytebase.com/dbcost/azure-flexible/instance/B1ms/)). تأخیر واقعی از ایران **اندازه‌گیری نشده** | Vercel و Neon منطقه‌ی اروپایی (فرانکفورت) دارند. تأخیر واقعی اندازه‌گیری نشده |

### مزیت مشترک: لایه‌ی AI در 1.0 ساده‌تر می‌شود
سرور خارج از ایران است، پس **از نظر شبکه** مستقیم به API مدل‌های زبانی (Anthropic و …) وصل می‌شود و سرور واسط لازم نیست. ولی این فقط مشکل شبکه را حل می‌کند. شرایط استفاده‌ی ارائه‌دهنده‌ی LLM درباره‌ی محل مشتری (ریسک R1) همچنان باقی است (ADR-0006).

## ۵. پیش‌شرط: آزمون دسترسی (نیم روز، هفته‌ی اول)

چون ریسک‌های H2 تا H4 **تأیید نشده‌اند**، پیش از ساخت این آزمون اجرا می‌شود (مالک: devops-engineer):

1. یک صفحه‌ی «سلام» و یک endpoint `/healthz` (با یک پرس‌وجوی دیتابیس) روی **هر دو** گزینه بالا بیاید: با دامنه‌ی پیش‌فرض و با دامنه‌ی اختصاصی.
2. از دست‌کم سه اتصال داخل ایران و **بدون فیلترشکن** باز شود: همراه اول، ایرانسل، و یک اینترنت ثابت. اگر Azure انتخاب شد، دو منطقه (UAE North و Germany West Central) جدا آزمون شوند.
3. ثبت شود: باز شد یا نه، زمان بارگذاری اولیه، و تأخیر `/healthz`.
4. **قاعده‌ی تصمیم:** گزینه‌ای انتخاب می‌شود که با دامنه‌ی اختصاصی از هر سه اتصال باز شود. اگر هر دو باز شدند، توصیه‌ی بخش ۷ اجرا می‌شود. اگر هیچ‌کدام باز نشد، به مدیر پروژه گزارش می‌شود تا بنیان‌گذار دوباره تصمیم بگیرد (مسیر ایرانی، بخش ۶).

| زمان‌بندی و صف با **pg-boss داخل Postgres** (ADR-0007)، نه Vercel Cron یا سرویس Azure | زمان‌بند با داده جابه‌جا می‌شود |
| فایل‌ها پشت رابط **`FileStorage`** با دو آداپتور: `azure-blob` و `s3` (برای MinIO یا ذخیره‌سازی S3-compatible ایرانی) | انتقال = عوض کردن `STORAGE_DRIVER` و کپی فایل‌ها |
| آپلود و دانلود فایل **از سرور ما** می‌گذرد (نه لینک مستقیم امضاشده) | کنترل دسترسی در یک جا؛ بدون تنظیم CORS اختصاصی |
| لاگ به stdout با فرمت JSON (pino)؛ بدون SDK مانیتورینگ اختصاصی (Application Insights و Vercel Analytics) | هر میزبانی لاگ stdout را می‌گیرد |
| فونت (Vazirmatn) و همه‌ی assetها از دامنه‌ی خودمان سرو می‌شوند | بدون وابستگی مرورگر به دامنه‌ی خارجی |
| **پشتیبان روزانه**: `pg_dump` رمزشده (با `age`) + فایل‌ها، در دو جا: (۱) ذخیره‌سازی ارائه‌دهنده، (۲) **یک مقصد داخل ایران** که از داخل ایران «کشیده» می‌شود (مثلاً یک VPS یا object storage ایرانی که هر شب فایل را دانلود می‌کند) | در قطعی بین‌الملل یا تعلیق حساب، آخرین نسخه‌ی داده داخل ایران موجود است |
| یک **runbook انتقال** که هر ۳ ماه یک بار روی یک VPS آزمایشی تمرین شود | انتقالِ آزمایش‌نشده انتقال نیست |

**هدف بازیابی پس از مهاجرت اضطراری:** RPO = ۲۴ ساعت (داده‌ی بعد از آخرین پشتیبانی که به ایران رسیده از دست می‌رود یا تا وصل شدن دوباره دیده نمی‌شود)، RTO = ۱ روز کاری.

**مسیر مهاجرت آینده (یک خط):** VPS ابری داخل ایران با Docker Compose (برنامه + Postgres + MinIO)، مثلاً لیارا ۲ vCPU / ۴ گیگ به قیمت ۲٬۶۵۰٬۰۰۰ تومان در ماه ([liara.ir/pricing](https://liara.ir/pricing/)، ۲۷ مهر ۱۴۰۵)؛ پارس‌پک و آروان گزینه‌های هم‌ارزند.

## ۷. تصمیم

**گزینه‌ی A — Azure** پیشنهاد می‌شود:
- **App Service Linux B1** (کانتینر، Always On)
- **Azure Database for PostgreSQL Flexible Server B1ms** (۳۲ گیگ، پشتیبان ۷ روزه، بدون HA)
- **Blob Storage** (LRS، سطح Hot)
- منطقه: بر اساس آزمون بخش ۵. اگر هر دو باز شدند و تأخیر UAE North کمتر بود، **UAE North**؛ وگرنه **Germany West Central**. برنامه و دیتابیس در یک منطقه باشند.
- رجیستری image: GitHub Container Registry. استقرار از GitHub Actions.

### چرا Azure و نه Vercel
1. **پردازه‌ی دائمی.** صف و زمان‌بند (pg-boss) بدون سرویس اختصاصی کار می‌کند. همین صف در 1.0 فراخوانی‌های LLM را با تلاش مجدد و سهمیه مدیریت می‌کند (ADR-0006). روی Vercel برای همین کار به Vercel Workflows/Queues وابسته می‌شدیم.
2. **قابلیت انتقال.** چیزی که روی Azure اجرا می‌شود (image داکر + Postgres) دقیقاً همان چیزی است که روی سرور ایرانی اجرا می‌شود. با توجه به H1، این مهم‌ترین معیار است.
3. **یک حساب خارجی به‌جای دو.** Vercel + Neon دو قرارداد و دو بند تحریم دارد.
4. **محدودیت ۴٫۵ مگابایت** Vercel با پیوست ۵ مگابایتی PRD تداخل دارد.
5. منطقه‌ی UAE North **ممکن است** تأخیر کمتری به ایران داشته باشد (اندازه‌گیری نشده).

### چه چیزی را از دست می‌دهیم
- سادگی «push = استقرار» و preview خودکار Vercel. با یک workflow ساده‌ی GitHub Actions (build image ← push به GHCR ← به‌روزرسانی App Service) جبران می‌شود. devops-engineer جزئیات را می‌نویسد.
- حدود نیم روز تنظیم اولیه‌ی بیشتر.

### اگر بنیان‌گذار Vercel را ترجیح دهد
معماری اجازه می‌دهد، با این تغییرها: (۱) Vercel **Pro** (نه Hobby)؛ (۲) Neon Launch در فرانکفورت با `fra1` به‌عنوان منطقه‌ی توابع؛ (۳) زمان‌بند: Vercel Cron هر ساعت `POST /api/internal/jobs/:name` را با سرآیند `X-Job-Secret` صدا می‌زند (این endpoint از ابتدا ساخته می‌شود؛ ADR-0007)؛ (۴) آداپتور `vercel-blob` و آپلود مستقیم از مرورگر برای فایل‌های بیش از ۴ مگابایت؛ (۵) مسئله‌ی صف 1.0 دوباره در ADR جدا بررسی شود.

## ۸. پیامدها

- devops-engineer: آزمون بخش ۵، زیرساخت به‌صورت کد (Bicep یا Terraform، ساده)، CI/CD، پشتیبان دوجایی، runbook انتقال، مانیتورینگ uptime از **داخل ایران** (یک بررسی ساده از یک VPS ایرانی، چون مانیتور خارجی قطعی ایران را نمی‌بیند).
- backend-engineer: قواعد بخش ۶ را رعایت می‌کند؛ هیچ SDK اختصاصی Azure جز داخل آداپتور `azure-blob`.
- security-reviewer: بررسی H5 و H7 و مدیریت کلیدها (Key Vault لازم نیست؛ تنظیمات App Service و secretهای GitHub کافی است).
- اگر قطعی بین‌الملل طولانی شود (پیشنهاد: بیش از ۷۲ ساعت، یا هر زمان که بنیان‌گذار بگوید)، runbook انتقال اجرا می‌شود.

## ۹. سؤال‌های باز (فقط بنیان‌گذار)
- **Q1:** حساب Azure (یا Vercel) و روش پرداخت به نام چه کسی و از کجاست؟ آیا با شرایط ارائه‌دهنده سازگار است؟ (H5، H6)
- **Q2:** آیا درباره‌ی نگهداری داده‌ی کاربران ایرانی روی سرور خارجی مشاوره‌ی حقوقی گرفته‌اید؟ (H7)
- **Q3:** آستانه‌ی اجرای مهاجرت اضطراری در قطعی اینترنت (پیشنهاد: ۷۲ ساعت) و مقصد پشتیبان داخل ایران (VPS یا object storage ایرانی؛ حدود ۰٫۵ تا ۱ میلیون تومان در ماه).
