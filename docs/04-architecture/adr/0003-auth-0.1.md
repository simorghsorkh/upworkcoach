# ADR-0003 — Authentication for 0.1: invitation + phone and password, with sessions in the database

- **Status:** Proposed (awaiting founder gate). The security-reviewer review is done, and changes **C1** and **C2** (`security.md` section 4) are applied in this version.
- **Date:** 27 Mehr 1405 (2026-10-19); security revision: 28 Mehr 1405 (2026-10-20); **reconciliation with the code of sprints 1 to 4: 30 Mehr 1405 (2026-10-22) (section 9)**
- **Author:** software-architect
- **Source of requirements:** PRD F1, `mvp-scope.md` (F1: no public sign-up and no OTP), `security.md` (C1, C2, SEC-P*, SEC-R*, SEC-T*, SEC-S*)

## Context
- There is no public sign-up. The admin (and, if allowed, a mentor) creates the user and gets a **single-use invitation link that expires in 7 days**, which they send themselves on Telegram.
- Login with **phone + password**. Password recovery with **admin approval**. There is no SMS in 0.1.
- Users are on phones and weak internet; login must be low-friction and persistent.
- We must not depend on an external authentication service (sanctions, shutdowns, migration).
- (Security C1) The invitation link gets forwarded on Telegram, and anything in the URL path remains in the host's HTTP logs, the app logs, the browser history and the `Referer`.
- (Security C2) The coach's phone number is public; a simple "per phone number" lockout becomes a tool for locking the coach out. The app runs behind the Azure App Service proxy, and the user's IP comes only from the proxy header.

## Options
| Option | Assessment |
|---|---|
| **A. Small in-house implementation:** argon2id + a `sessions` table + an httpOnly cookie, following well-known patterns (OWASP Session Management, The Copenhagen Book) | About 300 lines of understandable code; exactly our flow; revocable sessions; no external dependency |
| B. Auth.js (NextAuth) with Credentials | Does not officially support database sessions for credentials (JWT), so session revocation becomes hard; we would have to build the invitation flow ourselves |
| C. Better Auth | Complete and active, but email-centric; its phone plugin is designed for OTP; it imposes its own tables and routes |
| D. External service (Clerk, Auth0, Firebase) | Sanctions and shutdowns; rejected |
| E. JWT without database sessions | Immediate revocation (disabling a mentor, password change) is not possible; rejected |

## Decision: Option A

### 1. User creation and invitation
1. Admin `POST /api/v1/students` (or `/invitations` for a mentor) with name and phone → `users(status=invited)` (+ `students` for a student) → `auth_tokens(purpose=invite, expires_at=now+7d)`.
2. Token: 32 random bytes (`crypto.randomBytes`), base64url. Only its **SHA-256** is stored in the database.
3. **(Security C1) Link shape:** the token is in the **fragment**, not in the path or query:
   - Invitation: `${APP_BASE_URL}/invite#t=<token>`
   - Password reset: `${APP_BASE_URL}/reset#t=<token>`

   The browser does not send the `#…` part to the server. So the token does not appear in the host's HTTP logs, the pino logs, the `Referer`, or the Telegram link preview (which only GETs the static page). **No page or API route has a `:token` parameter** (test T-TOKEN checks this against `routes.manifest.ts`).
4. The API response returns the full link **only once**, with `Cache-Control: no-store`. The link never appears in `audit_log.data` or in logs (SEC-T8, SEC-L1). The UI shows a "Copy" button and a ready-made Telegram message text. If it is lost, "Regenerate link" revokes the previous token and is recorded in `audit_log` as `user.invite_link_created` (with the creator's role).
5. A duplicate phone number returns the error `409 PHONE_TAKEN`.
6. A mentor can create a student only when `settings.access.mentorsCanInviteStudents = true`, and the student is **automatically assigned to that mentor** (PRD section 5). Only the admin invites mentors and admins. For regenerating a link, a mentor has access only to a user with `role='student'` and `status='invited'` who is within their scope (security C3; ADR-0004).
7. **Bootstrapping the first admin:** a CLI script `pnpm admin:bootstrap --phone … --name …` that runs only when no admin exists. (Security C1, SEC-T6) The link from this CLI is valid for **1 hour** (not 7 days) and is printed only to that process's stdout, not to the app logs.

### 2. Accepting an invitation and resetting (security C1)
The `/invite` and `/reset` pages are **one shared, static component** (the server never sees the token). Order:
1. The page's JavaScript reads the token from `location.hash` (key `t`) and **immediately** calls `history.replaceState(null, '', location.pathname)` so that the token is removed from the address bar and history. The token stays only in the page's memory.
2. `POST /api/v1/auth/tokens/lookup { token }` → `200 { purpose: 'invite' | 'password_reset', displayName, expiresAt }`. A token that is nonexistent, used, revoked or expired all get the same response: `410 TOKEN_EXPIRED`. **The phone number (even masked) is not returned**, because the phone is now the second factor (item 3).
3. **Cheap second factor:** the acceptance form also asks for the user's **full phone number** (the name is shown, the phone field is empty). `POST /api/v1/auth/tokens/accept { token, phone, password }`:
   - The phone is normalized with the same `lib/phone` function and compared with `users.phone`.
   - Wrong phone → `422 VALIDATION_FAILED` with `fields.phone = "این شماره با این لینک هم‌خوانی ندارد"` ("This number does not match this link") and `auth_tokens.phone_mismatch_count += 1`. After **5** wrong phone numbers for one token → `revoked_at = now()` and `audit_log(auth.token_revoked_mismatch)` (SEC-T4). From then on, `410`.
   - Correct phone → password validation (section 3) → in **one transaction**: `UPDATE auth_tokens SET used_at = now(), used_user_agent = $ua WHERE token_hash = $1 AND used_at IS NULL AND revoked_at IS NULL AND expires_at > now() RETURNING …` (if no row is returned → `410`; this prevents two concurrent acceptances) → `password_hash` → `password_changed_at = now()` → `users.status = active` → **revoke all of the user's previous sessions** → new session → for a student invitation, `timeline_events(invite.accepted)`.
   - If the request carried another session cookie (e.g. the coach opened the link on their own phone), that session is also revoked, and before acceptance the page warns: «الان با حساب دیگری وارد شده‌ای؛ با ادامه، از آن خارج می‌شوی» ("You are currently signed in with a different account; if you continue, you will be signed out of it").
4. **No GET consumes or revokes a token** (SEC-T3). The `/invite` and `/reset` pages: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `<meta name="robots" content="noindex">`, no Open Graph tags, no external links at all.
5. Rate limiting for lookup and accept: key `token:ip:<ip>`, 30 failed requests in 15 minutes → 15-minute lock (SEC-R3).
6. **The phone is not verified with OTP** (there is no SMS in 0.1). The "forwarded link" risk is now reduced by four layers: the token is outside the URL, the full phone number is required, it is single-use, and "Invitation accepted: time and device type" (from `auth_tokens.used_at` and `used_user_agent`) is shown to staff on the users page and in the student record (SEC-T5), so that if a student says "the link didn't work", the coach can tell that someone else opened it.

### 3. Password policy (security C2)
- **Length:** students 8 to 128 characters; **admins and mentors 12 to 128 characters** (SEP-P2 is SEC-P2). UTF-8 byte cap: 512. **No** mandatory character-class or symbol rules (NIST SP 800-63B). Length is checked against the user's **current** role when the password is set or changed. A student never changes role (`api.md` section 3), so a password shorter than 12 never reaches a staff account. A role change between mentor and admin revokes sessions, but the previous password (which was already at least 12 characters) remains valid.
- **Blocklist** (SEC-P3): reject the password if it is in the local list of common and leaked passwords (a local file of about 100 thousand entries, no external API), or if it equals or contains the phone number (both the `0912…` and `912…` formats). The error message is in Persian and non-judgmental.
- **Password normalization (final decision; before the first hash is created, because changing it later invalidates every password)** (SEC-P1). The previous decision ("Persian digits in passwords are not converted") **was replaced**, because the same password may produce `ي`/`ی` or different digits on an Android keyboard versus Windows, and a user who types the "correct password" gets locked out. The function `normalizePassword(raw)` in `modules/identity/password.ts` runs **exactly the same** before hashing (setting and changing the password) and before verify (login):
  1. `raw.normalize('NFKC')`
  2. Persian digits (`۰`–`۹`) and Arabic digits (`٠`–`٩`) → `0`–`9`
  3. `ي` (U+064A) and `ى` (U+0649) → `ی` (U+06CC); `ك` (U+0643) → `ک` (U+06A9)
  4. **No** trim and **no** case change. Length is measured **after** normalization.

  Unit test: `"Abc۱۲۳يك"` and `"Abc123یک"` produce the same output; `" abc"` and `"abc"` produce two different outputs.
- **Hash:** argon2id (`@node-rs/argon2`); `memoryCost: 19456` (KiB), `timeCost: 2`, `parallelism: 1`, `outputLen: 32`; output in PHC format so the parameters travel with the hash; rehash on successful login if the parameters have changed (SEC-P4).
- **Concurrency:** at most **2** concurrent argon2 operations per instance (a simple queue in `identity`). Waiting more than 5 seconds in the queue → `503` with `Retry-After`. The dummy hash is created once at app startup (SEC-P5).
- Persian digits in the **phone number** are also converted to Latin digits (as before).

### 4. Login (security C2)
- `POST /api/v1/auth/login { phone, password }`. The phone is normalized (`۰۹۱۲…`, `0912…`, `+98912…`, `98912…` → `+98912…`) **before** the rate-limit keys are built (SEC-R7).
- The error response is always the same: `401 INVALID_CREDENTIALS`. If the user does not exist, is `invited` or is `disabled`, the dummy hash is still verified so that the response time does not leak information.
- **User IP (SEC-R4):** only the function `getClientIp(req)` in `server/http/client-ip.ts` reads the IP:
  1. Split `X-Forwarded-For` on `,` and trim.
  2. If `TRUSTED_PROXY_HOPS = n > 0`: take the **n-th value from the right** (on App Service `n = 1`, i.e. the rightmost value, which the Azure proxy itself added). Values to the left can be spoofed by the client and are **never** read. If the header has fewer than `n` values, the connection IP (`unknown` if unavailable) is used and a warning is logged.
  3. If `TRUSTED_PROXY_HOPS = 0` (local environment with no proxy): `X-Forwarded-For` is ignored.
  4. The port is stripped (`1.2.3.4:5678` → `1.2.3.4`; `[2001:db8::1]:443` → `2001:db8::1`). Whether App Service also sends the port is **not confirmed**; devops-engineer should check on staging.
  5. For rate-limit keys, IPv6 is truncated to the `/64` prefix. The full address is stored in `sessions.ip` and `audit_log.ip`.
  - `X-Real-IP`, `X-Client-IP` and other values are not read. If a CDN or another proxy is ever placed in front of App Service, `TRUSTED_PROXY_HOPS` goes up by one (devops-engineer's decision).
- **Three-layer rate limiting** (the `auth_throttle` table, because multiple app instances do not share memory; counting with `INSERT … ON CONFLICT DO UPDATE` in one transaction, SEC-R5):

  | Layer | Key | Threshold | Lock | Who bypasses it |
  |---|---|---|---|---|
  | 1. Phone + IP (SEC-R1) | `login:pi:<phone>:<ip>` | 5 failures in 15 minutes | 15 minutes | No one |
  | 2. Global per phone (SEC-R2) | `login:p:<phone>` | 20 failures in 1 hour | 1 hour | A request carrying **a valid device cookie of that same user** |
  | 3. IP (SEC-R3) | `login:ip:<ip>` | 30 failures in 15 minutes | 15 minutes | No one |

  - **Device cookie:** `__Host-uc_dev = base64url(userId) + '.' + base64url(HMAC-SHA256(DEVICE_COOKIE_SECRET, userId))` with `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=31536000`. It is set on every successful login or token acceptance (if another user signs in on the same browser, it is overwritten). Valid means the HMAC is correct (`timingSafeEqual`) **and** its `userId` equals the user who owns the phone number in the request. So an outside attacker can fill layer 2 for the coach's phone number, but the coach can still sign in from their own phone and laptop.
  - **New secret:** `DEVICE_COOKIE_SECRET` (32 random bytes). It replaces the unused `SESSION_SECRET` in ADR-0002. Recording it in the env contract (ADR-0002, `tech-stack.md`, `.env.example`) is part of **C7** and must be done before deployment. If it is empty or shorter than 32 bytes under `NODE_ENV=production`, the app does not start.
  - A successful login clears the `login:pi:<phone>:<ip>` key. Accepting a reset link clears the `login:p:<phone>` key.
  - **Counting is done exactly the same way for nonexistent phone numbers** so that a `429` does not reveal whether an account exists (SEC-R6). Lock response: `429 TOO_MANY_ATTEMPTS { retryAfterSeconds }` and nothing else.
  - `POST /auth/change-password`: key `pwchange:u:<userId>`, 5 failures (wrong current password) in 15 minutes → 15-minute lock.
- **Recovering the only admin from a lockout or a forgotten password (SEC-T7):** CLI `pnpm admin:reset-link --phone …`, which runs only from the server console (SSH into the App Service container): it creates a **1-hour** reset link and prints it to stdout, clears all `auth_throttle` keys for that phone number, and writes `audit_log` with `actor_id = null` and `data.via = 'cli'`. This replaces "manual SQL in production".

### 5. Session (security C2)
- Session token: 32 random bytes. Cookie `__Host-uc_session`: `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=<seconds until expires_at>`, no `Domain`. Only the SHA-256 is stored in `sessions`. The token is read only from the cookie (SEC-S6).
- **Session lifetime by role** (read from `users.role` when the session is created; a role change revokes all sessions, so a session never continues with an old role):

  | Role | Sliding | Absolute cap from `created_at` |
  |---|---|---|
  | Student | 30 days | 90 days |
  | **Admin and mentor** | **7 days** | **30 days** |

  Reason: a staff session reaches every student record and the CSV export, and there is no two-factor login in 0.1 (A9). `last_used_at` and the extension of `expires_at` (and the cookie's `Max-Age`) are written at most once every 15 minutes. (If the founder answers that mentors share devices, question S4 in `security.md`, the 7-day figure is lowered.)
- **Validation on every request** (API and RSC, SEC-S3): the session is not revoked or expired; `users.status = 'active'`; `sessions.created_at >= users.password_changed_at`; **the role is read from `users`**, not from a cache.
- On login and on token acceptance a new session is created (session fixation is not possible).
- **Revoking all sessions:** password change, password reset, invitation acceptance, user deactivation, role change, phone change by the admin, account deletion (ADR-0010). With `change-password`, the other sessions are revoked **and the current session is rotated** (new row and token) (SEC-S4). All with `audit_log(session.revoked_all)`.
- `GET /api/v1/auth/sessions` and `DELETE /api/v1/auth/sessions/:id`: the user sees their devices and signs them out. `DELETE` only with the condition `user_id = actor.userId`; otherwise `404`.
- Logout: `revoked_at`, cookie with `Max-Age=0`, header `Clear-Site-Data: "cache"` (SEC-S5). The device cookie is **not** cleared on logout (its purpose is recognizing the device, not authentication).
- Local environment: if `APP_BASE_URL` starts with `http://localhost`, the cookie names have no `__Host-` prefix and no `Secure` (`uc_session`, `uc_dev`). Under `NODE_ENV=production`, if `APP_BASE_URL` does not start with `https://`, the app does not start (SEC-S8).
- On every authenticated request, `users.last_seen_at` (at most every 15 minutes) and, for a student, `students.last_activity_at` (at most every 1 hour) are updated.

### 6. CSRF
- `SameSite=Lax` + checking the `Origin` header (must equal `APP_BASE_URL`) for all non-GET requests + requiring `Content-Type: application/json` (or multipart only for `/attachments` and `/imports/students`). A separate CSRF token is not needed. Strict details (missing `Origin` → `403`, exact comparison) in `security.md` SEC-C1..C5.

### 7. Password reset (security C1)
- On the login page the student taps "I forgot my password" → message: «به مشاور یا مربی‌ات پیام بده تا لینک تازه بفرستد.» ("Message your mentor or coach so they can send you a new link.") (No public endpoint; so no abuse is possible either.)
- Admin `POST /api/v1/users/:id/reset-link` → `auth_tokens(purpose=password_reset, 24h)` → response `{ resetUrl: "${APP_BASE_URL}/reset#t=<token>", expiresAt }` with `no-store` → sends the link manually → the user enters their **full phone number and new password** on `/reset` (the same `POST /auth/tokens/accept` as in section 2) → all previous sessions are revoked and the `login:p:<phone>` lock is cleared. Link creation is recorded in `audit_log` (without the link itself).
- **1.0:** SMS OTP behind an `SmsProvider` interface. Note: some Iranian SMS services may not accept requests from a foreign IP (**not confirmed**; while the server is on Azure, examine this in a separate 1.0 ADR).

### 8. What we do not have in 0.1
- Two-factor login for the admin (1.0 proposal: TOTP, before inviting a second admin or reaching 150 students; `security.md` section 9).
- Login with email or social networks.
- Phone change by the user themselves (only by the admin, recorded in `audit_log` as `user.phone_changed` and with all sessions revoked).
- Password re-confirmation for sensitive actions (SEC-S7): a recommendation for 0.1, **mandatory before inviting a second admin**.

### 9. Reconciliation with the implementation (aligned with code, sprints 1 to 4)
This section records the decisions and assumptions that backend-engineer made during the build (`docs/05-delivery/sprint-1.md`, "Assumptions" section), with an architecture ruling for each. Items that differ from the text of `security.md` are listed for security-reviewer approval in followup F-07.

|---|---|---|---|
| 9-1 | **Session cookie and sliding expiry** (section 5, SEC-S1) | Cookie `Max-Age` = **absolute cap** (students 90, staff 30 days). `sessions.expires_at` is sliding and is checked on every API **and RSC** request and extended every 15 minutes (sprint 1) | **Accepted.** RSC cannot write cookies; if `Max-Age` were sliding, a student who only views pages (without calling the API) would be logged out after 30 days, while their session is still alive on the server. ## Consequences
- **Positive:** No external dependency; immediate revocation; all authentication logic in the `identity` module and portable. The invitation token never appears in any log (C1). A deliberate lockout of the admin account no longer keeps them out (C2).
- **Negative:** We maintain the security code ourselves. Mitigation: security-reviewer review before deployment, and the automated tests T-AUTH, T-TOKEN and T-SESSION in `security.md` section 6.
- **Negative (C1):** The `/invite` and `/reset` pages do not work without JavaScript (only JS reads the token). This is acceptable, because the whole app requires JS. The student fills in one more field (phone) on acceptance; final approval with the founder (question S3 in `security.md`).
- **Negative (C2):** Two new environment variables (`DEVICE_COOKIE_SECRET`, `TRUSTED_PROXY_HOPS`) and one more cookie. Admins and mentors sign in again after every 7 days of inactivity.
- The 1.0 path (public sign-up with OTP) only adds `auth_tokens.purpose='otp'` and one endpoint; the tables do not change.
