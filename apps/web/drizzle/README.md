# drizzle — SQL migrations

The files are generated from the `schema.ts` files with `pnpm db:generate` and are kept in git. Read the SQL before committing.
An applied migration is never edited; a new change = a new migration. Run: `pnpm db:migrate` (tracking table: `drizzle.__drizzle_migrations`).
`0000` is the infrastructure table `_health`. `0001_identity_auth`: `users`, `auth_tokens`, `sessions`, `auth_throttle` (identity module), `audit_log` (admin) and `settings` (catalog) — sprint 1.
`0002_students_path`: `CREATE EXTENSION pg_trgm` (on Azure Flexible Server it must be allowed in `azure.extensions`), `tracks`, `platforms`, `learning_paths`, `stages` (catalog), `students`, `mentor_assignments`, `platform_profiles`, `profile_snapshots` (students), `stage_transitions` (path) — sprint 2.
`0003_tasks_timeline_reminders`: `task_templates` (catalog), `tasks`, `task_extensions`, `submissions`, `reviews` (tasks), `attachments` (files; CHECK "exactly one parent once attached"), `notes`, `timeline_events` (timeline), `reminders` (reminders) — sprint 3. The last statement (the FK `profile_snapshots.source_submission_id`) was written by hand to avoid an import cycle between the schemas. The seed now also adds 16 default stage task templates (`progress-tracking.md` 3-4) with fixed ids.

`0004_health_questions_checkins_milestones`: `milestone_types`, `canned_responses` (catalog), `question_threads`, `question_messages` (questions), `checkins`, `milestones`, `student_flags`, `student_health` (health), and the FKs from attachments to the question message and the milestone — sprint 4. The seed now also adds 5 milestone types (only "first contract or paid order" with `counts_for_north_star`), the canned response "red lines", and the settings row `checkin = { enabled: true }` (decision E5); a settings row that an admin has saved is not overwritten.

**Default data (seed):** after the migrations, `pnpm db:migrate` also runs `src/modules/catalog/seed.ts` (3 tracks, 8 platforms, the default path and the 9 stages of `learning-path.md`). Separately: `pnpm db:seed`. It is idempotent: the ids are fixed and inserts use `ON CONFLICT DO NOTHING`, so running it again adds nothing and does not overwrite admin edits (name, order, deactivation).

`0006_organizations` (ADR-0011, Coach Office sprint 1): `organizations` and `organization_memberships`; an `organization_id` column on all organization data tables, `sessions` and `audit_log` (optional); the `settings` key becomes `(organization_id, key)`. In the same migration the 0.1 data goes to the `default` organization (`«سازمان پیش‌فرض»`, "Default organization"): the oldest admin becomes the owner, every user gets a membership, an account the admin had deactivated gets an inactive membership, and `users.status` becomes the account status again (`active` or `invited`). Child tables take `organization_id` from their parent (the function and trigger `set_organization_id`; a child never sits in an organization other than its parent's). `users.role` stays for now and is dropped in the contract migration. Test: `tests/integration/migration-0006.test.ts` (0000 to 0005, 0.1 data, then 0006). **Before running on production** take a full `pg_dump`; after running, rename the organization with `pnpm org:rename --slug default --name "…" --new-slug …`.

`0007_user_preferences` (ADR-0013, Coach Office sprint 2): the `user_preferences` table (key `user_id`, `locale` with a CHECK on `fa` and `en`). It is a per-account preference, not per organization; that is why it has no `organization_id`. It only creates a new table and does not touch existing data.

`0008_programs` (ADR-0012, Coach Office sprint 3): `program_templates`, `curriculum_nodes`, `program_runs`, `run_nodes`, `run_staff`, `enrollments`, `enrollment_transitions` (programs module) with an organization trigger on the child tables. At the end, the function `ensure_legacy_program(org)` and two bridge triggers (`stages_sync_legacy_program`, `students_sync_legacy_enrollment`) are created, and for every existing organization a "Freelance mentoring" template and run (`«منتورینگ فریلنسری»`, the seeded name) is created with one enrollment per student (idempotent; the seed also calls it after every `db:migrate`). It does not touch the old data. **On production only after 0006 and 0007**, with a fresh `pg_dump`.

`0009_mentors` (Coach Office sprint 4): `enrollment_mentors` (programs module, with an organization trigger) and `mentor_profiles` (mentors module). The note-visibility CHECK now also accepts `private`. Two bridge triggers keep the old path's primary mentor in sync with `students.primary_mentor_id`. At the end, the `mentor_assignments` history and each student's current primary mentor are carried over. It does not touch the old data. **On production only after 0006 to 0008**, with a fresh `pg_dump`.

`0010_program_progress` (Coach Office sprint 5): the columns `tasks.enrollment_id` and `tasks.node_id` (FK with `ON DELETE SET NULL`, a partial unique index for non-cancelled tasks), `milestone_type_id` on `curriculum_nodes` and `run_nodes`, and the `node_completions` table with an organization trigger (`node_completions_set_organization_id`). It only creates new columns and a table and does not touch existing data. **On production only after 0006 to 0009**, with a fresh `pg_dump`.

`0011_sessions_goals` (Coach Office sprint 5b): the `mentoring_sessions` and `goals` tables (mentoring module) with organization triggers (`mentoring_sessions_set_organization_id` from the run and `goals_set_organization_id` from the enrollment), and the `tasks.session_id` column (FK with `ON DELETE SET NULL`). It only creates new tables and a column and does not touch existing data. **On production only after 0006 to 0010**, with a fresh `pg_dump`.

`0012_notifications` (Coach Office sprint 6b): the `notifications` table (notifications module): recipient (`user_id`), type with a CHECK on six types, actor (`ON DELETE SET NULL`), the related student (`ON DELETE CASCADE`), subject id, a small jsonb payload and `read_at`. The service writes `organization_id` itself (there is no parent row for a trigger to read it from). Three indexes: each person's inbox, unread (partial) and student (for account erasure). It only creates a new table and does not touch existing data. **On production only after 0006 to 0011**, with a fresh `pg_dump`.

`0013_scheduling` (ADR-0014, Coach Office sprint 7): four tables of the scheduling module: `availability_rules` (weekday, start and end in minutes with a CHECK of 0 to 1440, `template_ids` uuid[]), `availability_exceptions` (day, `off` or `extra`; CHECK: only `off` can be whole-day), `mentor_offerings` (key `(mentor_id, template_id)`, with a CHECK on the settings range) and `booking_requests` (status `pending`, `approved`, `declined`, `cancelled`; `enrollment_id` and `session_id` with `ON DELETE SET NULL`; a partial index on pending requests). The notification-type CHECK is rebuilt so that it also accepts three booking types. The service writes `organization_id`. It only creates new tables and does not touch existing data. **On production only after 0006 to 0012**, with a fresh `pg_dump`.

`0014_date_hours` (ADR-0014 amendment, Coach Office sprint 7b): `availability_exceptions` now holds the hours of one date. Adds `template_ids uuid[] NOT NULL DEFAULT '{}'`; **converts data**: `extra` rows become `hours`, and partial `off` rows (with a time range) are deleted, because a date's `hours` rows now say when the mentor is free (whole-day `off` rows stay). The kind and range CHECKs are rebuilt (`off` without a range, `hours` with a valid range). `mentor_offerings.horizon_days` defaults to 60 and accepts 1–180. **On production only after 0006–0013**, with a fresh `pg_dump`.
