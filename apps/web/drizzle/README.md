# drizzle — مهاجرت‌های SQL

فایل‌ها با `pnpm db:generate` از روی `schema.ts`ها ساخته می‌شوند و در گیت می‌مانند. پیش از کامیت SQL را بخوانید.
مهاجرت اعمال‌شده ویرایش نمی‌شود؛ تغییر تازه = مهاجرت تازه. اجرا: `pnpm db:migrate` (جدول ردگیری: `drizzle.__drizzle_migrations`).
`0000` جدول زیرساختی `_health`. `0001_identity_auth`: `users`، `auth_tokens`، `sessions`، `auth_throttle` (ماژول identity)، `audit_log` (admin) و `settings` (catalog) — اسپرینت ۱.
`0002_students_path`: `CREATE EXTENSION pg_trgm` (روی Azure Flexible Server باید در `azure.extensions` مجاز باشد)، `tracks`، `platforms`، `learning_paths`، `stages` (catalog)، `students`، `mentor_assignments`، `platform_profiles`، `profile_snapshots` (students)، `stage_transitions` (path) — اسپرینت ۲.
`0003_tasks_timeline_reminders`: `task_templates` (catalog)، `tasks`، `task_extensions`، `submissions`، `reviews` (tasks)، `attachments` (files؛ CHECK «دقیقاً یک والد پس از وصل شدن»)، `notes`، `timeline_events` (timeline)، `reminders` (reminders) — اسپرینت ۳. آخرین دستور (FK `profile_snapshots.source_submission_id`) دستی نوشته شده تا چرخه‌ی import بین schemaها پیش نیاید. seed اکنون ۱۶ قالب کار پیش‌فرض مرحله‌ها (`progress-tracking.md` ۴-۳) را هم با شناسه‌ی ثابت می‌افزاید.

`0004_health_questions_checkins_milestones`: `milestone_types`، `canned_responses` (catalog)، `question_threads`، `question_messages` (questions)، `checkins`، `milestones`، `student_flags`، `student_health` (health)، و FK پیوست‌ها به پیام سؤال و نقطه‌ی عطف — اسپرینت ۴. seed اکنون ۵ نوع نقطه‌ی عطف (فقط «اولین قرارداد یا سفارش پولی» با `counts_for_north_star`)، پاسخ استاندارد «خطوط قرمز» و ردیف تنظیمات `checkin = { enabled: true }` (تصمیم E5) را هم می‌افزاید؛ ردیف تنظیماتی که مدیر ذخیره کرده بازنویسی نمی‌شود.

**داده‌ی پیش‌فرض (seed):** `pnpm db:migrate` پس از مهاجرت‌ها `src/modules/catalog/seed.ts` را هم اجرا می‌کند (۳ شاخه، ۸ پلتفرم، مسیر پیش‌فرض و ۹ مرحله‌ی `learning-path.md`). جدا: `pnpm db:seed`. idempotent است: شناسه‌ها ثابت‌اند و درج با `ON CONFLICT DO NOTHING`، پس اجرای دوباره چیزی اضافه نمی‌کند و ویرایش‌های مدیر (نام، ترتیب، غیرفعال‌سازی) را بازنویسی نمی‌کند.

`0006_organizations` (ADR-0011، اسپرینت ۱ Coach Office): `organizations` و `organization_memberships`؛ ستون `organization_id` روی همه‌ی جدول‌های داده‌ی سازمانی، `sessions` و `audit_log` (اختیاری)؛ کلید `settings` می‌شود `(organization_id, key)`. داده‌ی 0.1 در همان مهاجرت به سازمان `default` («سازمان پیش‌فرض») می‌رود: قدیمی‌ترین admin مالک (owner) می‌شود، هر کاربر یک عضویت می‌گیرد، حسابی که مدیر غیرفعال کرده بود عضویت غیرفعال می‌گیرد و `users.status` دوباره وضعیت حساب می‌شود (`active` یا `invited`). جدول‌های فرزند `organization_id` را از والد می‌گیرند (تابع و trigger `set_organization_id`؛ فرزند هرگز در سازمانی جز سازمان والد نمی‌نشیند). `users.role` فعلاً می‌ماند و در مهاجرت contract حذف می‌شود. تست: `tests/integration/migration-0006.test.ts` (۰۰۰۰ تا ۰۰۰۵، داده‌ی 0.1، بعد ۰۰۰۶). **پیش از اجرا روی تولید** `pg_dump` کامل بگیرید؛ بعد از اجرا نام سازمان را با `pnpm org:rename --slug default --name "…" --new-slug …` عوض کنید.

`0007_user_preferences` (ADR-0013، اسپرینت ۲ Coach Office): جدول `user_preferences` (کلید `user_id`، `locale` با CHECK روی `fa` و `en`). ترجیح هر حساب است، نه هر سازمان؛ برای همین `organization_id` ندارد. فقط جدول تازه می‌سازد و به داده‌ی موجود دست نمی‌زند.

`0008_programs` (ADR-0012، اسپرینت ۳ Coach Office): `program_templates`، `curriculum_nodes`، `program_runs`، `run_nodes`، `run_staff`، `enrollments`، `enrollment_transitions` (ماژول programs) با trigger سازمان روی جدول‌های فرزند. در انتها تابع `ensure_legacy_program(org)` و دو trigger پل (`stages_sync_legacy_program`، `students_sync_legacy_enrollment`) ساخته می‌شوند و برای هر سازمان موجود قالب و اجرای «منتورینگ فریلنسری» با یک enrollment برای هر هنرجو ساخته می‌شود (idempotent؛ seed هم پس از هر `db:migrate` صدایش می‌زند). به داده‌ی قدیمی دست نمی‌زند. **روی تولید فقط بعد از ۰۰۰۶ و ۰۰۰۷** و با `pg_dump` تازه.

`0009_mentors` (اسپرینت ۴ Coach Office): `enrollment_mentors` (ماژول programs، با trigger سازمان) و `mentor_profiles` (ماژول mentors). CHECK نمایش یادداشت حالا `private` را هم می‌پذیرد. دو trigger پل، مشاور اصلی مسیر قدیمی را با `students.primary_mentor_id` هم‌زمان نگه می‌دارند. در انتها تاریخچه‌ی `mentor_assignments` و مشاور اصلی فعلی هر هنرجو منتقل می‌شوند. به داده‌ی قدیمی دست نمی‌زند. **روی تولید فقط بعد از ۰۰۰۶ تا ۰۰۰۸** و با `pg_dump` تازه.

`0010_program_progress` (اسپرینت ۵ Coach Office): ستون‌های `tasks.enrollment_id` و `tasks.node_id` (FK با `ON DELETE SET NULL`، یکتایی جزئی برای کارهای لغونشده)، `milestone_type_id` روی `curriculum_nodes` و `run_nodes`، و جدول `node_completions` با trigger سازمان (`node_completions_set_organization_id`). فقط ستون و جدول تازه می‌سازد و به داده‌ی موجود دست نمی‌زند. **روی تولید فقط بعد از ۰۰۰۶ تا ۰۰۰۹** و با `pg_dump` تازه.

`0011_sessions_goals` (اسپرینت ۵ب Coach Office): جدول‌های `mentoring_sessions` و `goals` (ماژول mentoring) با trigger سازمان (`mentoring_sessions_set_organization_id` از اجرا و `goals_set_organization_id` از عضویت)، و ستون `tasks.session_id` (FK با `ON DELETE SET NULL`). فقط جدول و ستون تازه می‌سازد و به داده‌ی موجود دست نمی‌زند. **روی تولید فقط بعد از ۰۰۰۶ تا ۰۰۱۰** و با `pg_dump` تازه.

`0012_notifications` (اسپرینت ۶ب Coach Office): جدول `notifications` (ماژول notifications): گیرنده (`user_id`)، نوع با CHECK روی شش نوع، انجام‌دهنده (`ON DELETE SET NULL`)، هنرجوی مربوط (`ON DELETE CASCADE`)، شناسه‌ی موضوع، داده‌ی کوچک jsonb و `read_at`. `organization_id` را خود سرویس می‌نویسد (ردیف والدی ندارد که trigger از آن بخواند). سه نمایه: صندوق هر نفر، خوانده‌نشده‌ها (جزئی) و هنرجو (برای پاک کردن حساب). فقط جدول تازه می‌سازد و به داده‌ی موجود دست نمی‌زند. **روی تولید فقط بعد از ۰۰۰۶ تا ۰۰۱۱** و با `pg_dump` تازه.

`0013_scheduling` (ADR-0014، اسپرینت ۷ Coach Office): چهار جدول ماژول scheduling: `availability_rules` (روز هفته، شروع و پایان به دقیقه با CHECK ۰ تا ۱۴۴۰، `template_ids` uuid[])، `availability_exceptions` (روز، `off` یا `extra`؛ CHECK: فقط `off` می‌تواند کل‌روز باشد)، `mentor_offerings` (کلید `(mentor_id, template_id)`، با CHECK روی بازه‌ی تنظیمات) و `booking_requests` (وضعیت `pending`، `approved`، `declined`، `cancelled`؛ `enrollment_id` و `session_id` با `ON DELETE SET NULL`؛ نمایه‌ی جزئی روی درخواست‌های در انتظار). CHECK نوع اعلان دوباره ساخته می‌شود تا سه نوع رزرو را هم بپذیرد. `organization_id` را سرویس می‌نویسد. فقط جدول تازه می‌سازد و به داده‌ی موجود دست نمی‌زند. **روی تولید فقط بعد از ۰۰۰۶ تا ۰۰۱۲** و با `pg_dump` تازه.

`0014_date_hours` (ADR-0014 amendment, Coach Office sprint 7b): `availability_exceptions` now holds the hours of one date. Adds `template_ids uuid[] NOT NULL DEFAULT '{}'`; **converts data**: `extra` rows become `hours`, and partial `off` rows (with a time range) are deleted, because a date's `hours` rows now say when the mentor is free (whole-day `off` rows stay). The kind and range CHECKs are rebuilt (`off` without a range, `hours` with a valid range). `mentor_offerings.horizon_days` defaults to 60 and accepts 1–180. **On production only after 0006–0013**, with a fresh `pg_dump`.
